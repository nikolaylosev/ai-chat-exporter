# Platform notes: claude.ai

What the extension needs from claude.ai, as observed in real traffic on 2026-10-13 (web app build `1791589889`, Pro plan). Every request listed here was made from a logged-in claude.ai tab and returned the response described. Items marked **unverified** were seen only indirectly or are still open.

Fixtures for all formats live in [`tests/fixtures/claude/`](../tests/fixtures/claude/). They come from test chats created for this purpose and deleted afterwards, and every identifier and personal value in them is replaced (see [Fixtures](#fixtures)).

## 1. Key findings

- **The REST API still serves full conversations as JSON**, including branches, tool calls and file references. The web app itself now reads conversations through a Connect RPC service with binary protobuf (`/claudeai-rpc/anthropic.bard.api.v1alpha.ConversationService/StreamTimeline`), but the extension does not need it.
- **Two generations of chats exist side by side.** New chats run as "sessions" in a cloud sandbox (`workspace_session_id` is set). Older chats have no session. Both use the same conversation JSON, but tools, generated files and artifacts work differently. In a sample of the account's 40 latest chats, 36 were older chats.
- **Original files are available.** Uploaded pdf, docx and png files were downloaded byte for byte from `/files/{uuid}/contents`. The `.extracted.txt` fallback is needed only for the old `attachments` field, which never had a binary.
- **Artifacts are now published pages** with their own id, versions and content domain (`*.frame.claudeusercontent.com`). Their source is downloadable for every version.
- Two endpoint families need extra request headers (section 2).

## 2. Request context

### Downloads and cookies (verified on a local stand)

A local HTTPS server answering as `claude.ai`, with a `SameSite=Lax` session cookie set in the browser, showed:

- the session cookie is sent by a page fetch, an extension page fetch, a service worker fetch and `chrome.downloads.download(url)`, given the `https://claude.ai/*` host permission;
- `chrome.downloads` interrupts on HTTP errors (`SERVER_FORBIDDEN` for 403, `SERVER_BAD_CONTENT` for 404, `SERVER_FAILED` for 500) instead of saving the error body;
- `.html`, `.svg`, `.js`, `.py` downloads are not flagged as dangerous;
- Chrome renames a file to match a known MIME type: `artifact.jsx` served as `text/plain` was saved as `artifact.txt`. Blobs of type `application/octet-stream` keep the requested name.

All requests run from the content script on `https://claude.ai`, so the user's session cookies apply. No tokens are handled by the extension.

**Organization id.** Every org-scoped path contains the organization uuid. It appears in the first response of `GET /api/organizations` (**unverified** in this session: the web app now gets it from `GET /edge-api/bootstrap`; both were called at start).

**Extra headers.** Most `/api/...` endpoints need nothing beyond cookies. Two families are different:

| Endpoint family                | Required                                                                                                         | Without it                                  |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| `/v1/code/sessions/{id}`       | `anthropic-version: 2023-06-01`, `anthropic-beta: ccr-byoc-2025-07-29`, `x-organization-uuid: {org}`             | 400 `anthropic-version: header is required` |
| `/api/frame/{artifactId}?org=` | `X-Frame-CP: go` (tested alone: enough; the web app also sends `X-Frame-Platform`, `X-Frame-Surface` and others) | 404 `not_found_error`                       |

**Bot protection.** The login page runs a Cloudflare challenge. API calls from an already logged-in tab were not challenged.

## 3. Endpoints

`{org}` is the organization uuid. All responses are JSON unless noted.

| Purpose                                | Request                                                                                                        | Notes                                                                                                                      |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| List chats                             | `GET /api/organizations/{org}/chat_conversations_v2?limit=30&offset=0`                                         | `{ data: [...], has_more }`. Offset pagination verified. The older `chat_conversations?limit=` still returns a plain array |
| One chat with all branches             | `GET /api/organizations/{org}/chat_conversations/{id}?tree=True&rendering_mode=messages&render_all_tools=true` | Section 4                                                                                                                  |
| Download an uploaded or generated file | `GET /api/organizations/{org}/files/{file_uuid}/contents`                                                      | Original bytes, `Content-Disposition: attachment; filename*=utf-8''<name>`. Verified for pdf, docx, png, xlsx, md          |
| List files in an older chat's sandbox  | `GET /api/organizations/{org}/conversations/{id}/wiggle/list-files`                                            | Older chats only; 404 for session chats. Section 6                                                                         |
| Download a file from that sandbox      | `GET /api/organizations/{org}/conversations/{id}/wiggle/download-file?path=<url-encoded path>`                 | `application/octet-stream` with `Content-Disposition`                                                                      |
| Chat's cloud session (artifacts)       | `GET /v1/code/sessions/{workspace_session_id}` + headers from section 2                                        | `response_shape.external_metadata.artifacts[]`                                                                             |
| Artifact metadata and access token     | `GET /api/frame/{artifactId}?org={org}[&ver={versionId}]` + `X-Frame-CP: go`                                   | `ver`, `history`, `files`, `assetToken`. Without `ver` the token is for the live version only                              |
| Artifact version list                  | `GET /api/frame/versions/{artifactId}?org={org}`                                                               | `history` and per-version `created_at`, `seq`                                                                              |
| Artifact source file                   | `GET https://{artifactId}.frame.claudeusercontent.com/_f/{versionId}/_src/{path}?__frame_t={assetToken}`       | Raw file as published. The token goes in the query; no cookie needed                                                       |
| List projects                          | `GET /api/organizations/{org}/projects_v2?limit=30&offset=0`                                                   | `{ data, pagination: { total, limit, offset, has_more } }`                                                                 |
| One project                            | `GET /api/organizations/{org}/projects/{projectId}`                                                            | `name`, `description`, `prompt_template` (instructions), `docs_count`, `files_count`                                       |
| Project text documents                 | `GET /api/organizations/{org}/projects/{projectId}/docs`                                                       | Array with full `content`                                                                                                  |
| Project binary files                   | `GET /api/organizations/{org}/projects/{projectId}/files`                                                      | Same shape as chat files; download with `/files/{uuid}/contents`                                                           |
| Project chats                          | `GET /api/organizations/{org}/projects/{projectId}/conversations_v2?limit=30&offset=0`                         | Same item shape as the chat list                                                                                           |

Calls the extension does not need but should recognize in traffic: `/claudeai-rpc/...ConversationService/{StreamTimeline,PerformAction,ReportViewing,GetNewConversationDefaults}` (protobuf), `/api/event_logging/v2/batch`, `/api/v2/rum` (telemetry).

## 4. Conversation format

Fixture: [`conversation-branches.json`](../tests/fixtures/claude/conversation-branches.json).

### Top level

`uuid`, `name`, `summary`, `model`, `created_at`, `updated_at` (ISO 8601, UTC), `settings`, `is_starred`, `is_archived`, `is_temporary`, `platform`, `current_leaf_message_uuid`, `chat_messages`.

The list endpoint adds `project_uuid`, `project`, `workspace_session_id` (set for session chats, `null` for older chats), `has_assistant_outputs` and `latest_assistant_output_kind` (`artifact`, `document`, `image` or `null`).

### Messages and branches

Each item of `chat_messages`: `uuid`, `parent_message_uuid`, `sender` (`human` or `assistant`), `index`, `created_at`, `updated_at`, `content` (blocks), `text` (legacy flat text), `attachments`, `files`, `sync_sources`, `truncated`, and sometimes `stop_reason` and `input_mode`.

`chat_messages` is a flat list of **all** messages in the tree:

- the root parent is `00000000-0000-4000-8000-000000000000`;
- editing a user message adds a new `human` message with the same parent as the original;
- **Retry** adds a new `assistant` message with the same parent as the original answer;
- `current_leaf_message_uuid` is the leaf of the branch the user sees. The active branch is the path from that leaf up to the root through `parent_message_uuid`.

`index` reflects creation order, not position in a branch. In session chats, the first message can be an assistant message with a single `prepare_session` tool call ("Set up for this session"), and indexes can skip numbers. Both are service details and should not be exported as conversation turns.

### Content blocks

Every block has `type`, `start_timestamp`, `stop_timestamp`.

| `type`        | Fields                                                                                                                        |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `text`        | `text` (Markdown), `citations`, sometimes `flags`, `citations_grouping_mode`                                                  |
| `thinking`    | `thinking`, `summaries`, `cut_off`, `truncated`, `hidden`, `thinking_hidden`. In the session test chats `thinking` was empty  |
| `tool_use`    | `id`, `name`, `input` (object), `message` (UI label), `integration_name`, often `display_content`, `icon_name`, `tool_origin` |
| `tool_result` | `tool_use_id`, `name`, `content` (array of blocks), `is_error`, sometimes `file_deliveries`, `display_content`, `meta`        |
| `image`       | `file_uuid` (refers to an entry in the message's `files`)                                                                     |

Tool names seen in the 40-chat sample:

- **session chats:** `Bash`, `Read`, `Write`, `Edit`, `Artifact`, `SendUserFile`, `Skill`, `ToolSearch`, `TaskCreate`, `TaskUpdate`, `AskUserQuestion`, `prepare_session`, MCP tools (`mcp__<server>__<tool>`);
- **older chats:** `bash_tool`, `view`, `create_file`, `str_replace`, `present_files`, `web_search`, `web_fetch`, `memory_*`, `visualize:read_me`, `visualize:show_widget`, `ask_user_input_v0`, `step_card_display_v0`, `Artifact`, plus the same MCP pattern.

**Web search** (`web_search`): `tool_use.input = { query, mode }`; `tool_result.content[]` items are `{ type: "knowledge", title, url, metadata: { site_domain, site_name, favicon_url }, is_missing }`. Fixture: [`legacy-block-shapes.json`](../tests/fixtures/claude/legacy-block-shapes.json).

## 5. Files from the user

Fixture: [`conversation-attachments.json`](../tests/fixtures/claude/conversation-attachments.json).

Uploads are listed in the user message's `files` array:

| Field                              | Meaning                                                                          |
| ---------------------------------- | -------------------------------------------------------------------------------- |
| `file_uuid` (same as `uuid`)       | Id for `/files/{uuid}/contents`                                                  |
| `file_name`                        | Original name                                                                    |
| `file_kind`                        | `document` (pdf), `image`, `blob` (anything else: docx, xlsx, ...)               |
| `size_bytes`                       | Original size; matched the downloaded file in every test                         |
| `thumbnail_asset`, `preview_asset` | Images and pdf only. Their URLs use `/api/{org}/files/...` (no `organizations/`) |
| `document_asset`                   | pdf in projects: `/api/{org}/files/{uuid}/document_pdf`, `page_count`            |
| `download_source`                  | `files-api`; present on `blob` uploads only                                      |

An image upload also appears as an `image` content block with the same `file_uuid`.

**Uploads in chats with a sandbox** (code execution) are also files in `/mnt/user-data/uploads/`, under the original name with spaces, punctuation and the dots before the extension replaced by `_` (`notes-0.1.98.vsix` is `notes-0_1_98.vsix`). The web app downloads them from there with `wiggle/download-file?path=…` (section 6). Seen on 2026-10-14: `/files/{uuid}/contents` answered 404 for such uploads (`.pptx`, `.zip`, `.vsix`, `.patch`, `.md`) while the web app downloaded them from the sandbox. The extension looks each upload up in `wiggle/list-files` (by `custom_metadata.filename`, else by the letters and digits of the name) and uses the sandbox address when it is there.

The older `attachments` array (12 messages in the sample) holds pasted or converted text without a binary: `{ id, file_name, file_size, file_type, extracted_content, created_at }`. `file_name` can be empty. These are the only case for `<name>.extracted.txt`.

## 6. Files generated by the model

### Session chats

Fixture: [`conversation-generated-files.json`](../tests/fixtures/claude/conversation-generated-files.json).

The model calls `SendUserFile` (`input.files`: names in the sandbox). Its `tool_result` carries `file_deliveries: [{ file_uuid, path }]`. Download each with `/files/{file_uuid}/contents`. The sandbox `path` gives the file name.

### Older chats

The model calls `present_files` (`input.filepaths`). Its `tool_result.content[]` items are `{ type: "local_resource", file_path: "/mnt/user-data/outputs/<name>", name, mime_type, artifact_publishable }`. There is no file uuid in the JSON.

Two ways to download, both verified on the same file with identical bytes:

- `GET /api/organizations/{org}/conversations/{id}/wiggle/download-file?path=<file_path>`;
- `GET /api/organizations/{org}/files/{uuid}/contents`, where the web app's uuid is a version-5 UUID that is not present in the REST JSON (probably derived from the path, **unverified**). The extension should use `wiggle/download-file`.

**Saved copies (seen 2026-10-14).** The web app does not read chats through the REST endpoint above: it uses a Connect RPC stream, `POST /claudeai-rpc/anthropic.bard.api.v1alpha.ConversationService/StreamTimeline` (`application/connect+proto`). Its first frame holds the whole chat; 4-byte keep-alive frames follow, and the server closes the stream itself (`Stream-Close-Reason: cadence`). For each presented file it gives the sandbox path and, when Claude kept a copy, `/api/organizations/{org}/files/{uuid}/contents` (a version-5 uuid found nowhere in the REST JSON). The copy is the file as it was presented, and it still downloads after the model deleted or rewrote the file in the sandbox, where `wiggle/download-file` answers 404. A file without a copy carries the web app's note in field 27 of its record, for example "This file was replaced by newer files."; the web app cannot download those either. File records come in two shapes: name, path, then the copy (uuid, address); or uuid, name, address, `sc:<uuid>`, then the path. Pairing by position takes the neighbouring file's copy in the second shape, so the extension (`adapters/claude/timeline.ts`) walks the protobuf without a schema and pairs a path with a copy only inside the smallest message that holds exactly one path. Copies replace sandbox addresses, and the note becomes the reason in the export. The web app's card for a replaced file may download the newest version of that file; the extension does not, since the content would not match the name.

`wiggle/list-files` returns `{ success, files: [paths], files_metadata: [{ path, size, content_type, created_at, custom_metadata: { filename, ... } }] }`. It lists both `/mnt/user-data/uploads/` and `/mnt/user-data/outputs/`. It returns 404 for session chats. The extension saves every file listed there that the chat's messages do not already link (slides, images an artifact uses, files the model never presented), attached to the last message of the user (uploads) or of the model (outputs) written before the file's `created_at`.

## 7. Artifacts

Fixtures: [`conversation-artifact.json`](../tests/fixtures/claude/conversation-artifact.json), [`artifact-meta.json`](../tests/fixtures/claude/artifact-meta.json), [`artifact-v2.html`](../tests/fixtures/claude/artifact-v2.html).

In both chat generations the model writes a file in its sandbox (`Write`/`create_file`, then `Edit`/`str_replace`) and publishes it with the `Artifact` tool. The tool result text contains `https://claude.ai/artifact/<shortId>` and the version id (`Version 2, version id 1791882915-2e7b`). Reconstructing content from `Write` + `Edit` inputs is possible but fragile; the published source is available directly.

Steps verified for a session chat:

1. The chat list item has `workspace_session_id`.
2. `GET /v1/code/sessions/{workspace_session_id}` (section 2 headers) returns `external_metadata.artifacts[]`: `{ artifact_id (uuid), kind: "frame", title, url (short link), updated_at }`.
3. `GET /api/frame/{artifact_id}?org={org}&ver={versionId}` with `X-Frame-CP: go` returns `history` (newest first), `files: [{ path, contentType }]` and `assetToken` for that version.
4. `GET https://{artifact_id}.frame.claudeusercontent.com/_f/{versionId}/_src/{path}?__frame_t={assetToken}` returns the file as published. A token for one version returns 403 for another.

The `_f/{versionId}/` path without `_src` is the rendered page with the viewer runtime injected; it needs a cookie set inside the claude.ai iframe and is not usable from a separate tab (403).

The artifact domain answers requests from `https://claude.ai` with CORS, so the content script reads the source as text. No host permission for the artifact domain is needed.

**Older chats** have no session. The `Artifact` tool result still names the short link and the version id, and the chat contains every `create_file` / `str_replace` call on the published file, so the file is rebuilt from them (`adapters/claude/artifacts.ts`). When the file was written another way (for example by a shell command), there is nothing to replay; the file is then taken from the chat's sandbox with `wiggle/download-file?path=<published path>` (section 6), which holds its latest state.

**Older chats with artifacts** (9 `Artifact` calls in the sample) have no session, so step 2 does not apply. How to map the short link to the artifact uuid there is open (section 9).

## 8. Projects

Fixtures: [`project.json`](../tests/fixtures/claude/project.json), [`project-docs.json`](../tests/fixtures/claude/project-docs.json), [`project-files.json`](../tests/fixtures/claude/project-files.json), [`project-conversations.json`](../tests/fixtures/claude/project-conversations.json), [`conversation-in-project.json`](../tests/fixtures/claude/conversation-in-project.json).

- **Instructions** are `prompt_template` of the project. `description` is the short description.
- **Knowledge base** has two parts. Text files (for example `.md`) are stored as **docs** with their full `content` in `/docs`; they have no binary. Other files (pdf, xlsx) are in `/files` and download byte for byte through `/files/{uuid}/contents`.
- **Project chats** come from `/projects/{id}/conversations_v2`. Each chat in the global list has `project_uuid` and `project`.
- Project uuids are version-7 UUIDs (`xxxxxxxx-xxxx-7xxx-…`); other ids are version 4.
- **Not yet seen in a real account:** a project list longer than one page, and the fields of a list item. The extension reads 50 per page until `pagination.has_more` is false and needs only `uuid` and `name` from each item; counts and dates are used when present.

## 9. Open questions

1. **Older-chat artifacts:** resolved by rebuilding the file from the chat (section 7). Fetching the published file would need a way to map `claude.ai/artifact/<shortId>` to the artifact uuid without a session; not needed so far.
2. **Inline widgets** (`visualize:show_widget`): what to save.
3. **Thinking text:** empty in session test chats; check whether older chats or other settings return it.
4. **Chat list completeness:** `has_more` paging was verified on small pages of a real account. The extension reads 50 per page until `has_more` is false; a full pass over 318 chats works on the test stand. Still to check on a real account with 300+ chats.
5. **Rate limits:** no 429 seen at about 2–3 requests per second.

**Out of scope:** chats from before 2025, including the old `artifacts` tool that kept artifact content inline. The project owner has no such chats, so the adapter does not handle that format; if one appears, its tool calls are exported like any other tool call.
